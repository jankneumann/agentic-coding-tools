# Learning: ri-14

## Decisions
- **reject_out_of_scope routes through park_item, not reject_out_of_scope_fix**: The scaffolded acceptance outcome named reject_out_of_scope_fix as the existing path for reject_out_of_scope. That function is a post-fix scope check (raises ScopeViolation on an already-applied diff) and takes no ledger item -- it cannot express 'don't fix this finding.' park_item(ledger, item, reason=...), already used for needs_human, is the one function generic enough; defer_to_followup and reject_out_of_scope now reuse it with a distinct reason string, so no new ledger mutation surface exists.
- **One decide() call per round, not one per finding**: classify_round() asks a single decide() call carrying a 'continue' Noul plus one 'disposition_<id>' Choice per blocking item, mirroring gatekeeper_shadow's multi-named-question shape. Keeps judgment cost flat regardless of how many findings are open.
- **Replay comparison is fixture-scoped, not production-scoped**: converge()'s trend list is a local variable, never persisted anywhere in this codebase; the one real ledger.json on disk (add-visual-code-explainer's) is an unrelated feature's end-state snapshot, not a round-trend sequence. replay_dispatch_counts() is a pure function over a caller-supplied round sequence; comparing against real production trends is deferred until autopilot persists that history, the same deferral shape ri-04/ri-06/ri-07 each used.
- **Disposition is load-bearing, so unavailability must default to today's behavior exactly**: Unlike the purely observational GATEKEEPER/phase-outcome shadow judgments, this judgment decides what gets dispatched. classify_round() degrades to {} on any unavailability, and the caller reads it with .get(item_id, 'fix_now') -- every blocking item defaults to fix_now, reproducing the pre-existing unconditional-dispatch behavior bit for bit. All 74 pre-existing convergence tests pass unchanged because TYPESAFE_API_KEY is unset in this environment.

## Recommendations
- No round-by-round ledger trend history is persisted anywhere today. A future item that wants to replay real production trends needs to add that persistence first -- this item deliberately does not, to keep its own scope to the disposition mechanism.
- rescope-review-convergence-disagreement-routing (a different roadmap, skill-rightsizing) also touches convergence_loop.py's disagreement handling. Not a scope conflict with this item, but worth checking for a merge conflict if both land close together.
