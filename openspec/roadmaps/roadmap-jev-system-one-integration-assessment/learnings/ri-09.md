# Learning: ri-09

## Decisions
- **Compaction helper is new work, not reuse**: The scaffolded acceptance outcome claimed normalize.py already had a 'compact event form'. It does not -- _compact_transcript() is new: filters NormalizedEvents to user/assistant/tool-result TEXT content, excluding tool_use's tool_input payload, truncated to a char budget from the end.
- **Closed spec/implementation drift in harness-engineering**: The existing 'Session Transcript Mining' requirement's 'Triage scores every ingested session' scenario already documented model-resolved triage ('resolve its model via the archetype system... single-shot struggle classification'), but triage.py was pure arithmetic with no archetype/LLM call anywhere. Filed as a MODIFIED requirement (not ADDED) against harness-engineering, since this item closes that drift rather than adding a new capability.
- **composite_score stays deterministic; only classification is judged**: struggle_level and flagged_for_deep_analysis are the only fields the judgment can override; composite_score and the four counters are always the deterministic values -- kept as facts even when the judged classification differs from what the weighted sum would have produced.
- **Two new judged-only fields added alongside, not replacing, the counters**: redirected_by_user and out_of_scope_work are new TriageScore fields (default None, judged-only) rather than replacements for user_correction_count/scope_violation_count -- acceptance outcome 3 explicitly keeps the four counters unchanged in the output schema.
- **Codex caught three real gaps a first pass missed**: The dry-run CLI flag never reached the new decide() call (silently breaking the documented "no API calls in dry-run" promise), sanitize_event_stream() was defined but never invoked anywhere in the executable pipeline (a real exposure now that compacted transcript text leaves the process), and the deep-analysis floor was hardcoded despite this item's own acceptance outcome demanding a config-held threshold. All three fixed; none were caught by the pre-push local test run because the tests exercised the functions directly rather than the CLI/pipeline wiring around them.

## Recommendations
- skills/collect-transcripts/prompts/triage_v1.md still isn't referenced by any .py file even after this item -- it documents the same four-dimension rubric this item's Choice/Noul questions cover, but wiring it in as literal prompt text (vs. this item's structured Choice/Noul criteria) was not attempted. Worth revisiting if the judged criteria ever need richer guidance than the inline criteria dicts provide.
- deep_analyze.py remains a free-text LLM path with no archetype resolution visible in its own .py file either (same as triage.py before this item) -- likely dispatched via a SKILL.md-level Task call rather than in-script. Not verified as part of this item's scope (deep_analyze.py explicitly out of scope per the rationale).
- skills/pyproject.toml and agent-coordinator/pyproject.toml both declare plain "system-one-decisions" with no [live] extra, so decide()'s import typesafe_sdk always fails there regardless of TYPESAFE_API_KEY -- every judged call site under skills/ (this item's, plus ri-06's gatekeeper_shadow, ri-07's phase_outcome_shadow, ri-14's convergence_disposition) is unreachable from the standard skills venv install today. This is ri-01/ri-02's own deliberate per-consumer opt-in design (only packages/gen-eval opted in via its own [decisions] extra), not a bug any one item introduced, but it means none of the judged paths shipped so far have ever actually run live outside a manually-configured environment. Worth a dedicated roadmap item to decide whether skills/agent-coordinator should opt in by default now that five call sites are wired and waiting on it -- a real dependency/security trade-off, not a mechanical fix, so likely needs the same kind of user check-in the still-deferred shadow-to-acting promotion item got.
