# Learning: ri-15

## Decisions
- **Protected-subject findings never enter the screen, but keep going to stage two unchanged**: The scaffolded acceptance outcome read 'a protected subject is never sent' literally as 'never sent to stage two either' -- this broke the existing test_protected_subject_survives_a_wrong_verdict test (a single-protected-finding batch would produce an empty stage-two batch, changing status from 'ran'). Confirmed by actually implementing the literal reading and watching the test fail, not just reasoning about it. Corrected interpretation: 'any call' means the new screen's calibrated-decision call -- no ground's verdict can override the veto anyway, so no call is worth spending on it. Protected findings still reach stage two exactly as before this item, where the existing post-verdict veto protects them unchanged.
- **A stage-two failure discards stage-one's tentative work too**: fact_check.py's own module docstring guarantees 'any failure to call the model... removes nothing'. Stage one is now also a model call, so a stage-two caller failure or unparsable response resets the whole batch to kept, including a finding the screen had already confidently resolved via Ground A in the same pass -- rather than letting a partial, unverified result survive a failure elsewhere in the same invocation.
- **The 'agreement rate' acceptance outcome is a wiring test, not a live-calibration claim**: No [live] extra is installed anywhere in this repo (confirmed identically by ri-09/ri-10/ri-11), so a genuine live-model agreement figure against the recorded fixture batch cannot be produced in CI. The new test proves the screen's wiring reproduces the fixture's own recorded Ground-A verdicts when given an answer set that agrees with them, and prints the resulting rate -- a live figure is deferred to a future validation-phase run, mirroring test_fact_check_fixture.py's own existing precedent for stage two's accuracy figures.

## Recommendations
- No existing OpenSpec capability requirement documented fact_check.run's pre-existing behavior at all before this item; the new requirement is scoped to the screen this item adds, not a full retroactive spec of the module. A future item could backfill the rest as its own scoped documentation task.
