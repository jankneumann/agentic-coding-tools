# Learning: ri-05

## Decisions
- **Judged batching lives beside match_score, not inside it**: Batching needs visibility across a whole file's candidate pairs, which a pairwise match_score(a, b) signature cannot provide, and review_ledger.py's own dedup matching (a separate call site) must stay unaffected. Added _judge_pairs as a sibling function called only from ConsensusSynthesizer._match_all; match_score itself is byte-identical to before (confirmed by its full existing test suite passing unmodified).
- **Fixture claim corrected before implementation: one real pair, one singleton**: The scaffolded acceptance outcome claimed both of pr484-consensus.json's two named real defects are cross-vendor pairs. Reading all 23 entries found only one genuinely is (the footer/percent-format defect, antigravity id 1 + pi id 14); the other (pi id 12, 'nodes that export returns') has no antigravity counterpart anywhere in the fixture -- a true single-vendor finding that cross-vendor matching cannot manufacture a match for.
- **Batching granularity shipped is per (primary, other_vendor), not per file globally**: The existing greedy _match_all loop resolves one other-vendor's candidates per primary finding at a time; unifying judgment into a single run-wide per-file call would have required restructuring that loop with materially higher regression risk, for a batching win no acceptance outcome or test currently requires. Documented explicitly in design.md rather than letting spec text overclaim a scope broader than what shipped.

## Recommendations
- Every roadmap item's fixture/dataset references need the same grounding treatment as its acceptance-outcome text: ri-04 corrected a missing dataset claim, ri-05 corrected a fixture-content claim (both real defects assumed to be pairs when only one was) -- read the actual referenced file before writing a test that assumes what it contains.
- When a feature description names an implementation shape ('batched as N questions over one shared per-file state') that the existing algorithm's structure doesn't cleanly support at that exact granularity, ship the closest faithful approximation and document the gap explicitly in design.md rather than silently narrowing scope or forcing a riskier rewrite to hit the letter of the description.
- ri-06 onward (GATEKEEPER, phase outcomes, shadow-mode items) should check whether their own roadmap-scaffolded acceptance outcomes reference specific fixtures, datasets, or sibling changes before implementation -- this is now the third consecutive item (ri-02 through ri-05, excepting ri-03's different class of correction) needing this exact kind of grounding.
