# Learning: ri-10

## Decisions
- **Vendor availability is judgment context, not a new hard gate**: The scaffolded acceptance outcome claimed a hard "fewer than 3 vendors forces lead_review" gate as existing behavior being preserved. It is not -- _compute_score treats vendor count as one additive term among four, and two existing tests (test_fewer_than_3_vendors_reduces_score, test_boundary_score_2_selects_alternatives) deliberately assert alternatives is reachable with only 2 vendors. A literal hard-gate implementation broke both tests, confirming the scaffolded outcomes 3 and 4 were mutually exclusive given real test-suite ground truth. Corrected via refine-roadmap before finishing implementation: available_vendors is now passed into the judged call state as context the judgment can weigh, never a pre-check, leaving the deterministic fallback and both boundary tests completely untouched.
- **design.md section matching is new work, mirrors derive_spec_file heuristic**: _design_section_for_package() is new -- no code anywhere already extracted a "design.md section for package X"; SKILL.md references to "the backend section" are prose guidance, not an implemented lookup. Splits on top-level markdown headings, matches by case-insensitive substring against the package id, returns None on no match, mirroring review_ledger.derive_spec_file's shape.

## Recommendations
- The skill-workflow capability spec's Implementation Strategy Selection requirement now documents the judged path; consider whether the Complexity Gate requirement in the same file (LOC/packages/deps thresholds) is a similar arithmetic-proxy candidate for a future roadmap item, following this same pilot pattern.
- The still-deferred shadow-to-acting promotion item resurfaced as the top ready item once this item completed, since its earlier reorder only pushed it past one subsequent item rather than the whole remaining batch. Re-deferred again during this item's own bookkeeping, this time past every currently-ready item rather than just the next one, so it stops needing a manual re-defer after each completion. The underlying blocker (no live decision extra installed anywhere in this repo, per the prior item's own finding) has not changed and will not resolve on its own as more items complete -- it needs the extra question resolved and a real shadow period run, not just its dependencies clearing again.
