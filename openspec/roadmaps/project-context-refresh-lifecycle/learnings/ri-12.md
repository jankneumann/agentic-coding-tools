# Learning: ri-12

## Decisions
- **The contract could not express a working service finding nothing**: The section schema requires non-empty hits when status=injected -- correct, an injected section with nothing in it is not a section. But that left a state=ready, current=true response returning zero results with no honest representation, and the implementation mapped it to unavailable/unknown_state: a correctly functioning service filed under a broken one. Same misreporting this roadmap exists to remove, pointed the other way, and worse than a missing feature because it sends a reader hunting an outage that never happened. D14 adds trigger no_context with TWO reasons, because they are different facts: index_returned_no_hits (the index held nothing) versus all_hits_omitted (it returned hits and our own budget kept none). Only the second could have been changed by raising a bound, and a reader deciding whether to raise SEMANTIC_CONTEXT_MAX_HITS needs to know which happened.
  - Rejected: Allowing hits: [] on an injected section -- removes the contradiction by removing the invariant; injected-but-empty is indistinguishable from a rendering bug
  - Rejected: Reusing `unavailable` with only a new reason -- the trigger is what consumers branch on and what an operator reads first
  - Rejected: One reason for both cases -- collapses a distinction that changes what the reader should do next
- **Two documented guarantees were aspirational until executed**: render_semantic_context documents 'never raises' and every consumer relies on it -- semantic context is an OPTIONAL input, and an optional input that can abort its consumer is not optional. The blanket guard covered _render, but the fail-closed _render_fallback on the next line re-read the SAME untrusted section through _requested_revision, so a Mapping whose .get raises escaped the function entirely. Found by wp-fallback-tests with a hostile Mapping, reproduced directly, fixed by re-rendering with no section rather than trusting it twice. A docstring is a claim, not a test.
- **Mutation testing audited the tests, not just the code**: Sub-agents found THREE tautological assertions in their own work: one comparing hits that necessarily differed in the field under test; one satisfied by 0.8123 when asserting max_hits=8 was in a section; one asserting an omitted path was absent when the renderer names omitted paths by design. Each was found because a mutation failed to make it fail. The strongest single result was a mutation of the scope-filtering branch caught by a wp-retrieval test written BEFORE no_context existed -- a pre-existing test catching a new mutation is far stronger evidence than one co-designed with its own invariant.
- **Six thin consumers held by a two-sided test**: D11's real risk is six copies of one algorithm drifting. ALGORITHM_TOKENS is derived at import from sc.OMISSION_REASONS, sc.BUDGET_ENV_VARS (keys AND values) and the pipeline function names; one test requires every token in the owner's section, another requires none in any consumer block. A value migrating fails both halves at once, and a new omission reason is covered the day it lands with no test edit.
- **A test CI never runs fails the same way as one that always passes**: skills/pyproject.toml listed the LEGACY coordination-bridge/scripts/tests but not tests/coordination-bridge, so ri-12's 50 try_code_search tests AND a pre-existing test_archetype_resolve.py were invisible to the default CI sweep. The package's own verification named the file explicitly and passed, which is exactly how the gap stayed hidden.

## Deviations
- Plan: D8's four fallback triggers → Actual: Five triggers; D14 adds no_context for a healthy index (reason: Discovered during wp-retrieval implementation. Amended D8 explicitly rather than silently rewriting it.)
- Plan: wp-integration scoped to its own six tasks → Actual: Also fixed a never-raises violation, added D14 reason prose, added tests/coordination-bridge to testpaths, fixed two install-portability defects, and regenerated the contracts inventory (reason: All five were found by packages that correctly REPORTED rather than fixed them, each falling outside its write_allow. Integration is where cross-package findings land.)

## Recommendations
- ri-13 owns enablement and is now unblocked. Semantic injection ships OFF; the flag-off invariant is proven end to end (6/6 consumers return injection_disabled and render EMPTY, with git, detection and the bridge each rigged to raise -- none was called).
- Wire work_package_resolver into start_code_search_runtime(): the work_package scope kind returns scope_rejected on every call today, so D2 routes around it with an explicit scope.
- Adding an enum value to a schema needs a matching renderer table entry. An unknown trigger fails closed to a confident WRONG explanation -- ours claimed 'no declared read scope' when a scope was declared.
- Fixture shape is a real hazard: ri-08's scopes object is duck-typed on ATTRIBUTES (a dict silently becomes an empty scope) and filter_scope calls scopes.allows(). Both bugs presented as wrong trigger values, not crashes, because the never-raises guarantee converts programming errors into plausible states.
- Two changes regenerating the same derived artifact create a SEMANTIC conflict git cannot see: main said 10 schemas, the branch said 11, the correct merged value was 12. Regenerate after rebase; never hand-merge a derived file.
