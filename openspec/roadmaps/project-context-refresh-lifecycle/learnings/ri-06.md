# Learning: ri-06

## Decisions
- **Clone-local Git-common-dir ledger over a coordinator service**: Durable operation records live under <git-common-dir>/project-context/refresh-operations and are shared across linked worktrees with no coordinator or database dependency; the deterministic manifest is a separate committable projection.
  - Rejected: Coordinator API + Postgres operation service
  - Rejected: Commit the entire mutable operation journal to Git
- **Separate the mutable ledger from the deterministic manifest**: operation.json carries volatile attempt/timestamp/lock state and is never committed; the manifest projection excludes volatile fields and sorts every array so identical logical state serializes to identical bytes and same-revision reruns are no-ops.
- **Fail closed at the contract boundary**: Status-dependent JSON-Schema (failed requires error, deleted artifact requires null digest, non-succeeded semantic index requires a fallback) plus model cross-field checks (duplicate producer ids, semantic indexed==requested revision, identity tuple hashes to operation id) reject rather than coerce a fresh-looking record.
- **Represent semantic readiness separately from deterministic freshness**: Adopting ri-03's recommendation, SemanticIndexReference is an opaque external operation/registry reference; any status other than succeeded at the exact requested revision carries a mandatory fallback and is never listed as a repository artifact.

## Deviations
- Plan: Verification runs skills/.venv/bin/ruff and skills/.venv/bin/mypy → Actual: Ran ruff and mypy --strict from agent-coordinator/.venv (both clean) (reason: ruff/mypy are installed only in the coordinator venv in this environment; skills/.venv has pytest + jsonschema.)
- Plan: Implement in the dedicated managed worktree from the start → Actual: Implemented in the roadmap worktree, then migrated the change to the openspec/add-durable-context-refresh-records worktree and opened draft PR #269 (reason: Resumed a session in which creating RI06's managed worktree had been the previously blocked step; consolidated onto per-proposal worktree semantics once confirmed.)

## Recommendations
- ri-04 (architecture refresh): use OperationStore for cross-process status and emit a ProducerResult with the architecture input fingerprint; do not reintroduce a subprocess-local singleton.
- ri-05 (deterministic producers): emit ProducerResult with safe repo-relative artifact paths + sha256 and validations; never embed content or absolute paths.
- ri-07 (orchestrator): create one operation per (repo, revision), record each producer result, then project a single manifest; keep exact-search fallback on any non-succeeded or mismatched semantic index.
- ri-11 (convergence): choose the canonical manifest target path at the sync point — the runtime intentionally claims no main-writing location and its manifest is byte-idempotent for a no-op convergence commit.
