### Alternatives Considered
- Run the gate twice -- at the merge base and at HEAD -- and diff the reports: rejected because Exact rather than inferred, but every producer reads working-tree bytes, so a run at the base needs a checkout there, contradicting the ratified requirement that the gate SHALL NOT write to the checkout. It also doubles gate runtime and leaves the base ambiguity unfixed: two runs against an ambiguous base are two ambiguous answers.
- Event gating only, with no attribution logic: rejected because Cheapest and achieves the headline outcome, but genuinely-introduced drift would stop blocking on pull requests, and main's own gate would stay environment-dependent exactly where its verdict becomes authoritative. The promotion would still not be safe, which is the point of the work.
- A remediation servo on all pull requests: rejected because Larger blast radius for the repository's first write escalation, and human pull requests already have an author who can run one command.
- Making --base a mandatory argument: rejected because Moves the ambiguity into every caller instead of resolving it, and breaks test_gate.py:824, which asserts the Makefile invocation matches CI's.
