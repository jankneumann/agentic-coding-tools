## 4. Decisions you need to make

### D-A. Is the work-package structure worth keeping?

9 packages with hand-maintained `write_allow` scopes, lock keys, and per-package verification
commands. Round 2 found stale task ranges in **every** package description, three packages
whose gates cannot pass, one package (`wp-eval`) whose first TDD task has **nowhere to write**
(eval tests live in `agent-coordinator/tests/test_evaluation/`, outside its scope), and a task
(8.8) that writes a file locked by another package.

*Option*: collapse to ~4 packages along natural boundaries (coordinator config / skills
dispatch / adapters+eval / docs+cleanup) and let the existing test suites be the gate.

### D-B. Are the bespoke gate scripts worth keeping?

`check_empirical_facts.py` and `check_roster_residue.py` exist because the original YAML
one-liner gates were vacuous. Both replacements are also defeatable.

*Option*: delete both. Use `git grep -lI` inline in CI against a committed manifest, and treat
"did the CLIs actually get invoked" as a human checkpoint rather than a scripted assertion —
it is not mechanically verifiable, which is why two attempts failed.

### D-C. How much doc surface is in scope?

Currently 11 user-facing files in, 43 narrative deferred. Codex (round 2 #6) argues the
`skill-workflow` spec delta **explicitly names 8 lifecycle `SKILL.md` files** as needing
provider-neutral prose, so deferring them makes the spec unsatisfiable by this change.

*Option*: either pull those 8 into scope, or narrow the spec delta.

### D-D. Scope of the change itself

Is one change the right container for: roster config + dispatch allow-lists + 3 eval backends
+ 3 transcript adapters + kanban fixtures + Makefile + docs + 3 unrelated pre-existing test
repairs? Round 2 suggests not.

*Option*: split into `ri-01a` (roster + allow-lists, unblocks the roadmap DAG) and `ri-01b`
(adapters, eval backends, docs).

## 9. Honest assessment

The multi-vendor review paid for itself twice over — it found a measurement error I could not
have found myself, because my own tooling produced it. But my two attempts to fix the
verification apparatus each introduced a fresh instance of the same class of defect (a gate
that passes without checking). That is the argument for **less apparatus**, not better
apparatus: the parts of this plan that keep failing review are the parts I invented, not the
parts that describe the actual work.
