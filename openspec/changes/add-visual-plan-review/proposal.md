# Add Visual Plan Review

## Why

The most expensive loop in our workflow is discovering — *after* `implement-feature`
has started — that a plan rested on a wrong assumption. Today an OpenSpec proposal is a
wall of markdown (`proposal.md`, `design.md`, `tasks.md`). To object to a specific claim,
the human must describe *where* the problem is in prose ("the third task under Phase 2 assumes
the coordinator is reachable…"). That prose is lossy, and `parallel-review-plan` /
`iterate-on-plan` receive free-form text rather than element-anchored feedback.

Analysis of [`kunchenguid/lavish-axi`](https://github.com/kunchenguid/lavish-axi) (captured in
[docs/proposals/lavish-axi-html-artifact-feedback.md](../../../docs/proposals/lavish-axi-html-artifact-feedback.md))
showed a better model: render the plan as a reviewable **HTML artifact**, let the human click a
specific element and attach a comment, and return **surgical coordinates**
`{selector, tag, text, prompt, target}` to the agent instead of prose. Their tagline — "HTML is
the new markdown" — names the bet we have already been making informally with rich artifacts.

We choose to **borrow the pattern natively** rather than depend on `npx lavish-axi`, so the
review surface fits our stack: a Python review server under `skills/shared/`, annotations
persisted as a git-tracked JSON artifact in the change directory (so `parallel-review-plan` and
the coordinator can consume them), and an interactive-review capability check short-circuiting the
browser loop whenever no human can drive it, in the same spirit our worktree ops short-circuit in
cloud harnesses. We keep the
annotation tuple wire-compatible with lavish-axi so we retain the option to interoperate later.

## What Changes

1. **New shared module `skills/shared/plan_review/`** providing:
   - `render.py` — transform an OpenSpec change's `proposal.md`, its `specs/**/spec.md` delta
     requirements and scenarios, and the `tasks.md` task DAG into a self-contained reviewable HTML
     artifact `.plan-review/<change-id>.html`, escaping/sanitizing all source content at render time
     (so a direct-from-disk or headless artifact can't execute injected markup). Sections:
     goal → current state → approach → requirements → task DAG, with each requirement, scenario, and
     task carrying a stable `data-plan-anchor` id so annotations target it precisely.
   - `server.py` — a local-first review server bound to `127.0.0.1` that serves the artifact,
     captures element/text-range annotations, runs an **open-time layout gate** (horizontal
     overflow, clipping, text overlap) that masks the artifact until it renders cleanly, and
     exposes a **long-poll** endpoint the agent blocks on for feedback.
   - `annotations.py` — the annotation schema + read/write of the git-tracked
     `plan-annotations.json` artifact.

2. **Annotation artifact** `openspec/changes/<change-id>/plan-annotations.json` — an accumulating,
   git-tracked list of `{uid, selector, tag, text, prompt, target, anchor, resolved}` records
   carrying a standard artifact header (`schema_version`, `generated_at`, `git_sha`, `generator`,
   `run_id`). Wire-compatible field names with lavish-axi's tuple.

3. **`plan-feature` gains an optional visual-review step** (behind a `--visual-review` flag,
   auto-skipped in headless/cloud). It runs **after `tasks.md` is generated** (plan-feature Step 6),
   so the rendered task DAG is populated — not immediately after `proposal.md`, which exists alone
   until the Step 5 approach-approval gate. It renders the artifact, serves it, long-polls for
   annotations, then folds the **unresolved** annotations into the existing `iterate-on-plan` pass as
   element-anchored findings, marking each `resolved: true` once its feedback has been applied.

4. **`parallel-review-plan` consumes `plan-annotations.json`** when present, attaching human
   annotations to the review context so vendor reviewers see the human's element-anchored concerns
   alongside their own findings.

5. **Environment-aware behavior** — a dedicated interactive-review capability check (cloud/headless
   profile via `environment_profile.detect()`, plus `CI`, display/browser availability, and an
   explicit override — not `detect()` alone) short-circuits the server/browser loop whenever no human
   can drive the review: the HTML artifact is still written (so it can be opened
   later or shipped as a PR attachment) and the step logs a "visual review skipped: headless" note
   instead of blocking on a poll that no human can answer.

6. **Update `openspec/specs/skill-workflow/spec.md`** via the delta in this change. Update only the
   canonical `skills/` sources; `.agents/skills/` and `.claude/skills/` mirrors are regenerated by
   `skills/install.sh`.

## What Doesn't Change

- The OpenSpec artifact set itself — `proposal.md`/`design.md`/`tasks.md` remain canonical and
  git-tracked. The HTML artifact is a *derived* review surface, rebuilt from them, never the source
  of truth.
- The `plan-feature` tiered-execution model (coordinated / local-parallel / sequential) — visual
  review is an additive, optional gate, not a new tier.
- `AskUserQuestion`-style prompts — they remain the right tool for small discrete choices; visual
  review targets large plans where *where* the feedback attaches matters.
- No new external runtime dependency — the review server is Python in the existing `skills/.venv`;
  we do **not** add `npx lavish-axi` or a Node dependency.
- Coordinator schema — a `plan_annotation` coordinator message type is explicitly **out of scope**
  for this change (see Approaches Considered → Decision C) and deferred to a follow-up.

## Approaches Considered

### Decision A — Adopt `npx lavish-axi` vs. build native (DECIDED: native)

Adopting the tool is faster to a working loop but adds a Node dependency to the skill runtime and a
long-poll protocol we do not own, and it cannot persist annotations into our change directory or
feed the coordinator without a bridge. Building native keeps everything in the Python skill stack,
makes annotations a first-class git-tracked artifact, and reuses `environment_profile.detect()` as
one input to the interactive-review capability check. We keep the annotation tuple wire-compatible so
a future swap-in remains cheap.

### Decision B — Where annotations live (DECIDED: git-tracked JSON in the change dir)

Alternatives were an ephemeral in-memory list (lost on server exit) or a coordinator row (couples
the feature to coordinator availability). A git-tracked `plan-annotations.json` survives restarts,
diffs cleanly in the PR, and is readable by `parallel-review-plan` with no coordinator dependency.

### Decision C — Coordinator `plan_annotation` message type (DEFERRED)

Routing annotations through the coordinator as a message type is attractive for multi-agent review
but expands scope and couples this change to coordinator transport. Deferred to a follow-up once the
local artifact-based loop has proven its value.

### Decision D — Layout gate severity (OPERATOR GATE)

lavish-axi blocks the human view on *error*-severity layout findings but shows *warning*-severity
ones. We adopt the same model. Because an *error*-severity finding masks the human view, it can't be
soft-gated — the agent must remediate (regenerate → re-audit) until errors clear before awaiting human
completion, or the run deadlocks. Only *warning*-severity handling is a Gate-1 operator decision in
`design.md` (surface to the agent vs. show only to the human).
