# Contracts — derive-descriptors-from-contracts

## Applicable sub-types

| Sub-type | Applies | Artifact |
|---|---|---|
| **JSON Schema** | **Yes** | `cli-contract.schema.json` — the tool-contract shape (design D5) |
| OpenAPI | Consumed, not authored | This change *reads* `openspec/contracts/<cap>/openapi/*.yaml`; it introduces no new HTTP endpoints |
| Database | No | No schema changes; gen-eval holds no persistent state |
| Events | No | No events emitted or consumed |
| Type generation | Deferred | Pydantic models are generated by the derivation scripts at implementation time (tasks 1.4, 2.2), not hand-materialized here |

## Why `cli-contract.schema.json` is not OpenAPI

Design D5. Two blockers:

1. **OpenAPI cannot express exit codes.** A tool's exit-code contract is a
   primary part of its interface — PR #277 pinned `0` / `2` / `64` for
   gen-eval — and there is no OpenAPI construct for it.
2. **A tool's flags are process configuration, not operation parameters.**
   `--fail-threshold`, `--output-dir` and `--verbose` are not parameters of any
   operation. Forcing them into an OpenAPI operation would be a lie a later
   reader has to decode — the same category error UP-4 corrected in the
   lifecycle.

The `binds_to` object is the bridge for the case where a CLI *is* a client of a
contracted service: it maps a flag onto an operation parameter with an explicit
location (`path` / `query` / `body` / `header` / `env` / `stdin`). It is
optional precisely because surface-local flags have nothing to bind to.

## On promotion to the stable location

On archival this schema moves to
`openspec/contracts/gen-eval-framework/schemas/cli-contract.schema.json`, per
`openspec/contracts/README.md`. Its `$id` already points at that destination so
the published identifier does not change when the change directory is archived.
