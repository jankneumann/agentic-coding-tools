# Plan Findings: wire-the-live-typesafe-client-thresholds-and-telemetry

## Iteration 1

Baseline `openspec validate --strict` passed on the plan-roadmap scaffold. Findings
below come from grounding the plan against the real `typesafe-sdk` package (installed
into a scratch venv and introspected directly — see design.md's "Real API surface"
section for what was checked) and against existing repo conventions, before writing
any code.

| # | Type | Criticality | Description | Proposed Fix |
|---|------|-------------|-------------|--------------|
| 1 | consistency | high | The acceptance outcome says threshold defaults "resolve from architecture.config.yaml", but that file is scoped exclusively to the architecture-report generator (`skills/refresh-architecture/scripts/reports/config_schema.py` — its schema has no threshold fields, and every existing key is about report sections/gates). Wiring `_route()`'s `act_floor`/`approve_floor` reads through it would either silently no-op or require adding unrelated fields to a generator config that has nothing to do with decision routing. | Follow `packages/context-eval`'s actual convention instead (its own rationale for the acceptance outcome's "context_eval convention" phrase): a package-owned data file (`packages/context-eval/corpus/manifest.yaml` there), loaded by the package itself, never a repo-root generator config. Add `packages/system-one-decisions/config/thresholds.json` + a small loader, and correct the acceptance outcome's wording in proposal.md. |
| 2 | feasibility | medium | The proposal says telemetry is recorded "to the existing Langfuse hook", but the only existing Langfuse integration (`skills/langfuse/scripts/langfuse_hook.py`) is a Claude-Code session-transcript hook — it has no relationship to `decide()` call sites and nothing to attach a per-call record to. | Mirror `decide_intent`'s already-established `event_sink` pattern (design D2 of `ri-01`) on `decide()` too: an optional caller-supplied callback receives one dict per completed call. Whether that reaches Langfuse is left to the caller (a future call-site migration item), keeping the package free of a langfuse dependency — consistent with why `decide_intent` avoided importing `skills/autopilot`'s state model. |
| 3 | completeness | medium | The scaffold's four `decide()` failure branches ("key absent", "network fails", "budget exceeded") are three, not four, despite the acceptance outcome text implying "one test per branch" for what reads as 3 named branches — but a 4th real branch exists and isn't named: the `live` extra not being installed at all (typesafe_sdk import fails). Both a fallback-only environment calling `decide()` and a live-extra environment with no key must both return `None`, not raise. | Name the 4th branch explicitly in design.md and tasks.md: "extra not installed" (lazy `ImportError` inside `decide()`) is its own tested branch, checked first, before the key check — a laptop with no key AND no extra installed must not attempt the import twice or generate a spurious traceback in logs. |
| 4 | assumptions | high | Neither `decide()`'s question-object shape nor how a caller is supposed to construct one was specified. Introspecting the actual `typesafe_sdk` package (real PyPI install, v0.7.0) shows `TypeSafeClient.system_one(state, questions: Mapping[str, Noul \| Choice \| Score \| ...])` — the SDK's own `Choice`/`Noul`/`Score` classes are the question objects. Requiring callers to construct these forces every caller to `import typesafe_sdk` directly, which contradicts the acceptance outcome "`typesafe_sdk` is imported inside `packages/system-one-decisions` and nowhere else in the repository." | Resolved via `AskUserQuestion` is not warranted here — no caller actually constructs a question in this roadmap item (call-site migration is explicit non-goal, same as `ri-01`). Record the constraint as design D2: `decide()`'s `questions` parameter keeps its current loose `dict[str, Any]` typing from `ri-01`; this item does not add a public question-type API. The real `Choice`/`Noul`/`Score` types are used only inside `packages/system-one-decisions`' own test suite (which is "inside the package", not a violation) to exercise `decide()`'s live path end-to-end against the real SDK types. |
| 5 | testability | medium | "the network fails" is unmeasurable as stated — the real SDK raises a rich exception hierarchy (`TypeSafeAPIConnectionError`, `TypeSafeAPITimeoutError`, `TypeSafeAuthenticationError`, `TypeSafeRateLimitError`, etc., all deriving from `TypeSafeError`). A test needs a concrete exception class to raise from a mocked client. | Catch `typesafe_sdk.TypeSafeError` (the common base every real SDK exception derives from, confirmed via introspection) in `decide()`'s live path; test with at least `TypeSafeAPIConnectionError` and `TypeSafeAuthenticationError` raised from a monkeypatched client to prove the catch is broad enough without being bare `except Exception`. |

## Resolution

All five findings are addressed in this iteration's `design.md` (D1–D5) and
`tasks.md`. No findings remain above the `medium` threshold after this pass.
