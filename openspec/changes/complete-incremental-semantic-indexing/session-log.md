### Decisions
1. **Copy forward immutable revision storage** `architectural: code-search` — A compatible ready ancestor supplies unchanged rows while CocoIndex processes only added/changed eligible files; every ready revision remains isolated.
2. **Fingerprint policy, pipeline, and embedding parameters** `architectural: code-search` — Exact commit plus model/dimension is insufficient when scope, chunking, dependency version, or provider parameters change.
3. **Prove source and eligibility before content access** `security: code-search` — Exact clean HEAD, repository containment, deny precedence, and hard secret/generated exclusions prevent a correctly labeled index from containing forbidden content.
4. **Heartbeat lease ownership** `reliability: code-search` — Long embedding runs can exceed the ri-01 lease; current-token renewal prevents concurrent takeover while stale workers remain unable to complete.
5. **Treat the coordinator gateway as an opt-in OpenAI-compatible provider** `architectural: llm-gateway` — Code search consumes the inference data plane without importing coordinator control-plane code or making remote embeddings the default.
6. **Accept inherited roadmap approval for planning gates** `architectural: project-context-refresh` — The explicit `$autopilot-roadmap project-context-refresh-lifecycle` command approves the roadmap-selected direction and automatic progression without per-item pauses.
7. **Fence publication with attempt-specific storage** `reliability: code-search` — Lease heartbeats protect registry ownership, while staging tables/manifests plus a current-token atomic publish prevent stale workers from corrupting ready storage.
8. **Select a thin Postgres target adapter** `architectural: code-search` — CocoIndex owns source/chunk/embed processing; storage_pg owns copy-forward, verification, and publication because those operations require an explicit fencing contract.

### Alternatives Considered
- Stable mutable staging table followed by immutable snapshot: deferred because it adds namespace-wide locking, another mutable lifecycle, and crash recovery around snapshotting.
- Full rebuild per revision: rejected because it fails changed-file embedding acceptance.
- Global content-addressed embedding cache: deferred because it introduces shared privacy, retention, and invalidation boundaries.

### Trade-offs
- Accepted copying unchanged Postgres rows over a pure CocoIndex memoization solution because revision isolation stays explicit and independently verifiable.
- Accepted a migration that replaces the ri-01 uniqueness constraint over encoding fingerprints into namespace names because namespace identity must remain stable and human-readable.

## Phase: Implement (2026-07-23)

**Agent**: codex-autopilot-roadmap | **Session**: N/A

### Decisions
1. **Keep CocoIndex state on the filesystem** `architectural: code-search` —
   Pinned CocoIndex 1.0.13 interprets `Settings.from_env(...)` as an LMDB state
   path. The CLI therefore derives stable state below the proven Git common
   directory (or an explicit outside-worktree override) and never passes a
   Postgres DSN to CocoIndex.
2. **Publish manifests through the registry in the storage transaction**
   `reliability: code-search` — The storage publisher renames verified attempt
   storage and invokes the registry-owned manifest publication against the same
   transaction and current lease token, so either both become visible or both
   roll back.
3. **Treat changed zero-chunk files as completed work**
   `architectural: code-search` — The final manifest records every eligible
   changed path, including files that produce zero chunks, so verification
   proves full path coverage without inventing storage rows.
4. **Use resource-gated live evidence, not unconditional skips**
   `reliability: code-search` — Six destructive end-to-end cases require an
   explicit opt-in, scratch DSN acknowledgement, and explicit provider. Pure
   fixture and contract assertions always run.

### Alternatives Considered
- Passing `POSTGRES_DSN` to `coco.Settings.from_env`: rejected after checking the
  pinned upstream implementation; the argument is an LMDB filesystem path.
- Publishing a copied manifest directly from the storage module: rejected
  because registry ownership and lease fencing would be split across
  transactions.
- Treating scanner/provider failures as one generic runtime error: rejected in
  favor of sanitized but actionable error codes.

### Trade-offs
- Accepted a small explicit Postgres adapter and per-attempt tables to make
  stale-write isolation independently testable.
- Accepted a project-local lockfile for the optional indexing environment so
  pinned CocoIndex and cocoindex-code compatibility is reproducible.
- Deferred live ParadeDB/embedder execution where credentials and acknowledged
  scratch resources are unavailable; all target, lifecycle, and fixture
  contracts remain mandatory and non-skipping.
