## Design Decision Trace

| Decision | Rationale | Implementation | Why This Approach |
|----------|-----------|----------------|-------------------|
| D1 | The repository's files are the record; the coordinator holds a copy | `replace_snapshot` overwrites the project's row with the pushed set | Per-gate add and remove calls would let the copy drift from the files after one missed call |
| D2 | A snapshot is read and written whole | Migration 047: one row per project, gates and source errors in a JSONB object; replace is update, then insert if no row was updated | A row per gate would need a delete-and-insert transaction for every push, and the database client has no upsert |
| D3 | Which projects are listed is an operator decision | `GateProjectionConfig` reads `GATE_PROJECTION_PROJECTS`; empty means none | Without a list, a repository that never pushed could not be reported as missing |
| D4 | A snapshot ages without any write happening | `list_pending` compares `received_at` with `GATE_PROJECTION_STALE_SECONDS` on every read | A stored status would need a background job to keep it true |
| D5 | The same gate must keep its id across pushes | `gate_id` is the first 16 hex digits of SHA-256 over project, source, roadmap id, item id, change id, gate and dispatch id | A counter or random id would change between collections and break decide-by-id |
| D6 | Only a record waiting for a person belongs in the listing | The collector takes `parked` attempts that have a gate and any non-null loop-state `pending_gate`; a `blocked` outcome with no parked attempt and archived changes are skipped | Listing a gate that refused would show history as work |
| D7 | The approval service already owns deadlines and decisions | The listing reads `list_pending` once and looks up the remaining referenced ids with `get_requests` | Copying approval state into the snapshot would create a second, staler copy |
| D8 | The coordinator can decide only what it owns | `decide` calls the approval service, or returns 409 with the gate's `answer_hint` | Writing a decision into a repository's files from the coordinator would make it a second writer |
| D9 | The collector needs one authenticated POST | `push` calls `CoordinatorHttpClient.request` directly | A `try_*` bridge helper would add a capability flag, a probe and a bindings entry for one caller |
| D10 | The posture, not the record, says how a gate is disposed now | `_Dispositions` reads `TRUST_POSTURE.md`; a missing file gives `block`, an invalid one gives `block` and a `source_errors` entry | A disposition stored on the record would be the one in force when it was written |
