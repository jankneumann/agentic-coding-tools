### Decisions

2. **Postgres (ParadeDB) backend instead of stock sqlite-vec** `architectural: code-search` — Index persists across ephemeral cloud sessions, one shared fleet index, hybrid pg_search BM25 unlocked, no new storage silo
3. **Vendor the 2-file backend patch, attempt upstream PR** `architectural: code-search` — No storage-backend registry upstream; patch is ~300-400 lines; Apache 2.0 permits either outcome
4. **Per-repo chunk tables (code_chunks__<slug>)** `architectural: code-search` — Zero query changes, DROP TABLE unload, no cross-repo index contention
5. **Coordinator-side query embedding with registry consistency check** `architectural: agent-coordinator` — Cloud agents lack model access; embedder mismatch must be a hard error, not silent degradation
6. **Expose as read-only tool/endpoint, never MCP resource** `architectural: agent-coordinator` — Resources are not proxied in http_proxy mode (coordination_mcp D6); read/write split keeps indexing out of query paths

### Alternatives Considered
- Adopt as-is (sqlite-vec, per-project daemon/MCP): rejected because Ephemeral cloud containers rebuild the index every session; N warm daemons; no hybrid BM25; bypasses scope enforcement
- Build natively on base cocoindex framework: rejected because Re-implements ~5,600 working lines (chunker registry, language detection, embedder pacing, CLI, MCP server)
- Hand-rolled pgvector index without cocoindex: rejected because Owns chunking, incremental tracking, and 28-language parsing — the greenfielding the codeviz proposal warns against

### Trade-offs
- Accepted Carrying a small vendored patch with hard version pins over Waiting for upstream backend pluggability because Patch is 2 files; fixture tripwire test makes upgrades loud
- Accepted Vector-only retrieval in phase 1 over Hybrid BM25 from day one because Hybrid is a service-internal ranking change (D3); shipping the surface contract first de-risks integration
