### Alternatives Considered
- Run simplify as a trailing sub-step inside IMPL_ITERATE (no new phase): rejected because Conflates behavior-changing iteration with behavior-preserving refactor in one outcome, runs before IMPL_REVIEW so review fixes re-introduce seams, and has no clean dual-run-failure outcome.
- Run SIMPLIFY after VALIDATE, before SUBMIT_PR: rejected because goal_gate binds DONE to the latest VALIDATE record postdating the report; post-VALIDATE commits either break the gate or force a second VALIDATE.
- Add a ninth review axis `test_quality`: rejected because Axis participates in cross-vendor consensus matching; would touch the synthesizer, the 8-axis prose in both review skills, and the fitness-functions spec, and collides with two active schema-reshaping changes.
- Fold the phase into fix-autopilot-archetype-and-apply-outcome: rejected because Widens a change that is nearly done; a separate change keeps the spec amendment reviewable on its own.
- Put simplify inside validate-feature: rejected because validate-feature is a judge with an explicit mutation boundary; a validator that changes the head it reports on invalidates its own evidence.
